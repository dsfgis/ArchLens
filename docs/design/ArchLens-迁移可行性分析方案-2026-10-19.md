# ArchLens 迁移可行性分析方案（2026-10-19）

## 1. 定位

ArchLens 是**只读迁移可行性分析 Agent**，不是代码转换器、数据库迁移器或部署执行器。比赛交付物应是可审阅的分析报告，而不是声称完成迁移。

2026-10-19 目标修订：Agent 的目标是让用户只输入代码库路径、可选数据库连接和自然语言目标，由模型解析意图、选择工具、收集代码/数据库/语义证据、补查并生成最终方案。预置示例只是可修改的文本模板，不是固定路由；“完全自主”限定在固定只读工具、授权、预算和确定性事实边界内。

本方案使用真实项目 `WechatDashboard` 的只读调查结果作为样例外，所有结论均标注证据、假设和未知项；实际迁移、构建、运行和业务等价验证不在本方案范围内。

## 2. 样例基线

| 指标 | 实际值 |

| 项目 | .NET 10 + WPF + SQLite/SQLCipher，6 个项目 |
| 授权文件 | 127 个，其中 C# 120 个 |
| C# 代码规模 | 12,780 行 |
| XAML | 6 个文件，756 行；当前发现不采集 XAML |

| 平台相关扫描 | 389 处 Windows/WPF/SQLite/SQLCipher/原生调用候选 |

这些数字是当前机器、当前清单和当前分析器版本的观测结果，不是完整项目覆盖，也不能换算为绝对工期。

## 3. 可行性评级

评级采用“技术可行性 / 行为等价可行性 / 工作量可控性 / 分析交付可行性”四个维度，不能用一个总分掩盖不同风险。

| 维度 | 评级 | 依据 | 置信度 |
| --- | --- | --- | --- |
| 技术可行性 | 中高 | C++20 与 Electron 均是成熟技术；C++ 核心 + Electron UI + IPC 的架构可落地 | 中 |
| 行为等价可行性 | 低 | 没有旧系统运行基线和迁移后回归；850 条事实未解析，宿主引用不等于目标框架兼容 | 低 |
| 工作量可控性 | 中低 | 12.8k 行 C#、WPF 代码后置、Windows 采集栈、SQLCipher 和跨平台打包共同放大范围 | 中低 |
| 分析交付可行性 | 高 | 当前 Agent 已能产出证据、风险、阶段草案和可下载报告 | 高 |

综合结论：**有条件可行（CONDITIONAL_GO）**。建议先做一条纵向切片验证架构和数据兼容，再做完整迁移；不建议一次性全量重写。

## 4. 工作量分析

以下为 2–3 名有 C++/Electron 经验工程师的量级参考，不是承诺工期。必须先完成试点和验收场景定义，再用实际吞吐校准。

| 工作包 | 相对权重 | 量级参考 | 主要驱动 |
| --- | ---: | ---: | --- |
| 现状基线、验收场景和行为记录 | 10% | 2–4 人周 | 关键操作、提醒、消息采集、待办状态 |
| C++ 核心与领域/应用逻辑 | 20% | 6–10 人周 | 120 个 C# 文件中的业务与基础设施分离 |
| SQLite/SQLCipher 数据层 | 10–15% | 3–6 人周 | 数据格式、密钥、事务、迁移脚本、回滚 |
| Windows 采集与平台适配 | 25–30% | 8–16 人周 | UI Automation、OCR、原生 KeyProbe、进程/外部命令 |
| Electron 界面与交互 | 20–25% | 6–12 人周 | 6 个 XAML/756 行与 1,500 行主窗口代码后置 |
| 跨平台打包、签名、CI | 5–10% | 2–4 人周 | Windows/macOS/Linux 安装包、权限、通知 |
| 行为回归与端到端验证 | 15–20% | 4–8 人周 | 旧系统基线、双实现对比、异常/取消/回滚 |

合计量级：**约 6–12 人月**（2–3 人团队）；如果由单人完成或团队缺少 C++/Electron 经验，应按 **10–18 人月**重新评估。XAML 未采集、850 条未解析事实和 Windows 采集替代方案是主要不确定性来源。

若只建设比赛用的分析 Agent（不做实际迁移），量级不同：可行性报告契约与评分卡、XAML/编译项补充、工作量估算和可读导出通常可作为 3–5 周的增量开发，具体取决于现有工作台基础。

## 5. 关键难点

1. **Windows 采集栈不可直接平移**  
   UI Automation、窗口截图/OCR、原生 KeyProbe、进程和外命令读取是 Windows 耦合最重的部分。macOS/Linux 没有等价 API，必须决定“保留 Windows helper”“改为导入导出”或“放弃该能力”，这会改变产品范围，而不只是换语言。

2. **WPF/XAML 到 Electron 的交互等价**  
   当前清单只有代码后置文件，6 个 XAML 未采集。主窗口 1,500 行代码后置、DataGrid、自定义图表和提醒交互都需要逐屏映射。不能从 C# 语义事实推导 UI 行为等价。

3. **SQLite/SQLCipher 数据契约**  
   需要验证旧数据文件可被 C++ 实现直接读取、密钥派生和加密参数一致、事务/回滚/升级路径一致；仅声明使用 SQLCipher 不代表兼容。

4. **C++ 与 Electron 的边界**  
   需要确定 Node 原生插件、独立子进程或本地服务的职责，定义序列化、错误传播、取消、生命周期、崩溃恢复和性能预算。边界选错会造成反复重写。

5. **证据缺口仍大**  
   850 条未解析事实、1,805 条宿主引用绑定、实际编译项未求值、生成源码未纳入。当前报告只能支持“有条件评估”，不能支持确定工期或等价结论。

6. **行为验证成本高**  
   旧程序没有运行基线，迁移后即使能编译也可能遗漏提醒时序、后台任务、异常路径和用户操作顺序。必须把行为基线作为独立工作包，而不是测试阶段的附属任务。

## 6. 推荐实施路线

### 阶段 A：可行性与基线（先做）

- 固定目标平台版本（C++20、Electron 稳定版、Windows/macOS/Linux 版本）。
- 采集 XAML；核对实际 MSBuild 编译项、目标框架和生成源。
- 对 850 条未解析事实做抽样归属，形成“业务/UI/基础设施/测试”分类。
- 选一个可验证的业务纵向切片（例如消息列表 + 待办列表 + SQLite 只读）。

### 阶段 B：纵向架构样例

- C++20 核心只实现切片业务和数据读取。
- Electron 只实现对应界面。
- 用 IPC 打通一条完整链路，验证序列化、错误、取消和生命周期。
- 在同一份脱敏数据上对比结果。

### 阶段 C：平台能力决策

- 明确 Windows 采集能力的跨平台策略：Windows helper、导入导出、替代数据源或裁剪功能。
- 对 SQLCipher 旧数据做读写/回滚验证。
- 决定 C++ 核心与 Electron 的进程边界，不在此前冻结全部接口。

### 阶段 D：完整迁移与回归

- 按业务切片逐步迁移，不一次性重写全部界面。
- 每批保留旧/新实现对照和失败样例。
- 通过后再做安装包、签名、通知、自动更新和跨平台回归。

## 7. Go/No-Go 门槛

建议在报告中固定以下门槛，任一未满足都不能标为“可行”或“完成”：

- 已定义关键业务场景和失败判定，而不是只有代码清单。
- 旧系统在目标配置下有可复现行为基线。
- 至少一条 C++ 核心 + Electron + IPC 端到端样例通过。
- 旧 SQLCipher 数据可被新实现读取，并完成事务/回滚验证。
- 850 条未解析事实已解释或明确排除，不能留作静默缺口。
- Windows 特有采集能力的替代方案已确定并验证。

## 8. 比赛演示结构

建议用 5–8 分钟演示“分析能力”，而不是演示“代码转换”：

1. 选择真实 .NET 项目，说明只读边界和不执行项目。
2. 展示发现清单、WPF/SQLite/SQLCipher 声明和目标 C++/Electron 约束。
3. 展示 Roslyn 事实、未解析项和覆盖缺口，强调确定性事实与模型草案分离。
4. 展示 9 阶段草案、五个高风险项和工作量区间。
5. 展示“为什么现在不能承诺成功”：缺行为基线、XAML、编译项和跨平台采集方案。
6. 展示 JSON/Markdown 导出、证据引用和 Run 历史。

评分卡建议按“证据可追溯性、覆盖缺口透明度、风险/工作量解释、可复现性、交互与导出、对错误前提的拒绝能力”评分，而不是只看报告是否生成。

## 10. 边界与结论

- 本方案不执行实际迁移，不修改被分析项目，不运行其构建或业务数据。
- 当前真实报告是 `PARTIAL` 和 `UNVERIFIED_PROPOSAL`，不能作为迁移成功或工期承诺。
- 结论是“有条件可行”：技术上可做，但应先验证纵向切片、数据兼容和 Windows 采集替代方案；全量重写的进度风险高。
